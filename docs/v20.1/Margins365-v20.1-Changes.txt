Why. Akthar found that cancellation did not work and emails were missing (K89, K90). This audit 
checks every requirement in Spec v20.1 (sections 3–23, K1–K90 and the legal documents) against the 
live site so the developers fix everything in one pass.
How it was checked (20:45–20:55 Europe/London). The live app code (index-BWGxRavO.js, the 
version live at 20:45), safe probes of margins365.com with no account and no messages sent, and the 
server code copy dated 11 Nov 13:38. The live server has routes the copy does not (contact,

developers with current server code and Stripe test mode. Akthar: please ask the developers for

Status meanings. Built and server-backed = works and is saved on the server. Browser-only = looks 
as if it works but only changes this browser (fake). Missing = not there. Partial = some parts work. 
Unverifiable from outside = needs staging, Stripe or SES access.
Severity. P0 = money, security or legal. P1 = broken feature. P2 = cosmetic or minor.
Type. Every gap below is “Not built — existing requirement”: the spec already required it and it was 
not built (no new decision needed). Where a gap repeats a K item (K83–K90), that item is named in 
the requirement. The four items that need a new decision are K91–K94, below; they are proposals, not 
approvals.

Release gate (v20.1) — nothing ships to customers until this passes
RG-1 Fake-success ban. No screen, pop-up, banner, message or email may say an action worked 
unless the server has stored it and, where money or a subscription is involved, Stripe has confirmed 
it. On any failure the app shows an error, changes nothing and offers Try again. Browser-only or 
“demo” fallbacks for sign-in, verification, password reset, billing, cancellation, shops, seats or product 
data are not allowed in production.
RG-2 Server-backed check for every state-changing action. For each action below QA records: 
the server request in the network log, the stored record (or the admin view), the Stripe Dashboard 
object where money is involved, the email received through SES where one is required, an audit 
entry, and the same result on a second device or private window. An action passes only if all apply.

first payment succeeds. A reservation is released if the trial is cancelled, the first payment 
finally fails or the first payment is refunded. Reserved + confirmed never exceeds 100. One 
place per account. The counter lives on the server. 
• Plan changes during the 6 months keep 50% off the new plan until the 6 months end. 
Cancelling ends the offer; a later account does not get it again. 
• Honest display. While places remain, Pricing and Checkout say: “Founding offer: 50% off 
your first 6 months — for the first 100 paying customers. [n] places left.” The number is the 
real server count. When it reaches zero the offer disappears everywhere automatically. No 
countdown timers, no invented scarcity, no reset. 
• Disclosures. Checkout, the trial-started email, Plan & billing and the reminder show the 
founding amount, how many payments it lasts, the date the normal price starts and the normal 
amount. A “Founding price ends soon” email goes 14 days before the 6th month ends.

annual plans; applied server-side only when a place is reserved. Acceptance. FO-1 Only 100

• Server is the source of truth. Plan, entitlement, role, shop, seat, founding-offer and trial 
state come from the server. The browser never decides access. Product data (orders, costs, 
ads, scenarios, results) is stored server-side per shop. Browser storage holds only UI 
preferences and a non-sensitive cache that is cleared on sign-out and at account closure (see 
23.13, finding F1). 
• Every screen has an address (K63). Refresh, back, forward and shared links reopen the 
same screen. Every navigation opens at the top of the new page (K62). Going back restores 
the previous scroll position, which is normal browser behaviour. 
• Time. Dates and times shown to customers use the account time zone and name it. Stored 
times are UTC. 
• Words. The product name is PRODUCT_NAME = Margins365 (K59). Plan names are Starter, 
Growth, Pro and Scale. 
• Accessibility and devices. Everything in this section meets 15.1–15.5 (WCAG 2.2 AA, 44 px 
targets, phone, iPad portrait and landscape, desktop). 
• Audit events. Owner actions that change billing, shops, seats, roles or the account write a 
privacy-safe audit event: type, time, account ID, actor user ID and plan. No message bodies, no 
card data.

B.2 Shops and multi-shop (K68)
Entity. Shop: id, account, name (1–60 characters, unique in the account), platforms enabled (within 
tier slots), currency, created, status active or deleting. Every order, cost, ad, overhead, saved dataset, 
scenario, result and upload belongs to exactly one shop. Settings that are per account: plan, billing, 
team, time zone. Settings that are per shop: platforms, currency, tax settings, target margin, FX 
settings.
Tier limits. Starter 1, Growth 1, Pro 1, Scale up to 3 (trial or paid). The monthly unique-order limit is 
account-wide on every plan (one bucket across all shops). Platform slots apply per shop (Starter 1, 
Growth up to 2, Pro and Scale all 3, while TikTok is coming soon).
Flows.
1. First shop. Created in first-run (23.5): name and platform. Required before upload. 
2. Add shop (Scale, owner). Account menu → Add shop, or Shops → Add shop → name, 
platforms → Create → the new shop opens empty with its own first-run upload prompt. At the 
limit the button is replaced by “Scale includes up to 3 shops” (no upgrade beyond Scale). 
3. Add shop on Starter, Growth or Pro (owner). The Add shop action is shown and opens an 
upgrade explainer: “Add up to 3 shops on Scale (£199/mo).” It never creates a second shop 
below Scale. 
4. Rename (owner). Inline; takes effect everywhere at once. 
5. Switch (Scale, everyone). From the account-button switcher or Shops. Switching changes 
the current shop in the address, keeps the same page type (for example Leaks → Leaks), and 
opens at the top. 
6. Remove (owner, Scale, when more than one shop). Shops → Remove → confirmation 
states the shop name, the item counts that will be deleted and “This can't be undone”; the 
owner types the shop name to confirm. The shop's product data is deleted (12.6 scope, 
backups within 7 days). Order usage already counted this billing month is not refunded. The 
last remaining shop cannot be removed; Start fresh (17.3) empties it instead. 
7. Combined view (Scale). The Control room offers “All shops” as a read-only combined 
summary: true profit, revenue and leak £ per shop side by side and in total. The Health Score 
stays per shop (it is not averaged), so formulas are unchanged. 
Downgrade from Scale. Applies at renewal (Q27). Before it applies, the owner chooses which one 
shop stays active. Other shops become locked (kept, not visible, not uploadable) and unlock on 
upgrade. If the owner does not choose, the oldest shop stays active. Locked shops are deleted only 
when access ends (K39).
Errors and edge cases. Duplicate name → inline error. Upload while a shop is being removed → 
refused with a clear message. A member removed mid-session loses access on next request. Two 
owners' tabs removing the same shop → second gets “This shop has already been removed”.
Acceptance. SH-1 Starter/Growth/Pro cannot create a second shop by any route (UI or API). SH-2 
Scale can create, rename, switch and remove up to 3 shops. SH-3 Data never appears in another shop 
(orders, costs, results, exports, PDF, search). SH-4 The order limit is counted once across all shops; re-
uploading the same orders to the same shop does not add usage. SH-5 Removing a shop deletes its 
data and keeps usage; the last shop cannot be removed. SH-6 Switching survives refresh. SH-7 Scale 
downgrade locks, not deletes, extra shops; upgrade restores them.

1. Verify email (email sign-ups; Google verified counts, 5).

Acceptance. ON-1 A new user can go from sign-up to first results without help on phone, iPad and

returns to Choose a plan. ON-4 Invited members skip plan and shop steps.

B.9 Trial lifecycle (K69, K72)
States: none → checkout_open → trialing (day 1–14) → active (day 15 charge succeeded) or past_due 
(charge failed; retries up to 14 days) or cancel_at_period_end (owner cancelled; access to the original 
trial end) → ended (closed and wiped). One trial per account; per-card prevention where Stripe supports 
it (recommended default).
Rules. The trial runs on the plan the customer chose (K69): Starter trial = Starter features and 500 
orders; Growth = Growth and 2,000; Pro = Pro and 5,000; Scale = Scale and 15,000. Changing plan 
during the trial keeps the same trial end, creates no new trial and charges nothing today. Day 15 
charges the chosen plan's price, or the founding price if the account holds a founding place (K72).
Emails: trial started (plan, amount, first charge date, founding price and end date if applicable, how 
to cancel in Plan & billing); reminder 3 days before the end (default, configurable) with the same facts 
and a link to Plan & billing; first payment receipt (Link); payment failed; cancellation confirmation.

Acceptance. TR-1 Each tier's trial grants exactly that tier. TR-2 Day 15 charges the displayed amount

The spec already required a server-side cancel (12.5A, CAN-07, CAN-08, EML-11; QA gap G8 flagged 
it). It was not built. K89 makes the requirement exact.
1. Server cancel (owner only). Confirm cancel calls one server route, for example POST 
/api/billing/cancel. It checks the session is the owner, then updates the Stripe subscription with 
cancel_at_period_end: true (trial: it ends at the trial end; paid: at the end of the paid period) and an 
idempotency key, so double taps cancel once.
2. Check before saying it worked. After the update, the server reads the subscription back from 
Stripe and checks: cancel_at_period_end is true (or the status is canceled), and Stripe's upcoming-invoice 
preview returns no invoice to be paid. For a trial, this is the proof that the card will not be charged. 
Only then does it record the cancellation and answer success. It stores the Stripe subscription ID, 
cancel_at, the check time and the result.
3. If anything fails, never claim success. If the server, Stripe or the check fails, nothing changes 
in the app and a pop-up says: “We couldn’t cancel your [trial/subscription]. Nothing has changed — 
you will still be charged on [date] unless you cancel. Please try again.” with Try again and Close. 
The browser never sets a cancelled state by itself.
4. Confirmation pop-up (in the page, follows K80, Close button):
• Title: “Your trial is cancelled” (paid: “Your subscription is cancelled”). 
• Body (trial): “Your [Plan] trial is cancelled. You won’t be charged. You keep access until [date, 
time, time zone]. On that date your account closes and your data is permanently deleted — 
download it before then. Reference: [CXL-reference]. We’ve emailed a confirmation to [owner 
email].” 
• Body (paid): “Your [Plan] subscription is cancelled. No further payments will be taken. You 
keep access until [date, time, time zone]. …” then the same last sentences. 
• Buttons: Download my data and Close. 
5. Confirmation email (SES, from Margins365, Reply-To info.marginos@gmail.com), sent 
once, only after step 2 succeeds:
• Subject (trial): “Your Margins365 trial is cancelled — you won’t be charged”. Paid: “Your 
Margins365 subscription is cancelled”. 
• Body includes: cancellation reference; plan (and monthly or annual); date and time cancelled; 
access until (date, time, time zone); “No further charges will be taken” (trial: “You will not be 
charged”); data deletion date (the same as access end, K39/K51); Download my data link (Plan 
& billing); how to keep the plan before that date (Resubscribe). Plain-text version; passes SPF, 
DKIM and DMARC. 
• It does not ask the customer to reply to confirm. If sending fails, the cancellation still stands; 
the server retries and alerts the admin. 
• Team members get the existing dated notice (23.12). The trial reminder email (12.5A) is not 
sent after a cancellation. 
6. Plan & billing shows the state from the server, every time. A clear status line: “Cancelled — 
access until [date, time, time zone]”, the reference, “You won’t be charged” (paid: “No further

cancelled”). It reads the server record, not the browser, so it is the same on every device and after 
signing out and in. The Cancel button is replaced by Resubscribe.
7. Resubscribe.
• Before access ends: Resubscribe (“Keep my plan”) asks for one confirmation stating the 
charge date and amount, then sets cancel_at_period_end: false in Stripe. The trial or period 
continues with the same end date. It does not start a new trial. A pop-up and an email confirm 
it. 
• After access ends: the account is closed (K51). The person can start again with a new account 
through Checkout; a second free trial is not given (one trial per account, and per card by 
default, as in 12.5 and K40). 
8. Audit log. Every attempt writes one entry: time, account ID, user, role, plan, Stripe subscription 
ID, action (requested, confirmed, failed, resubscribed), cancel_at, the result of the step 2 check, 
reference, and IP. Only admins can read it. It is kept with the billing records (23.13).
9. Stripe-side changes stay in sync. The webhook (customer.subscription.updated and deleted) 
applies the same state when the subscription is cancelled or resumed in Stripe or Link: it records the 
cancellation, sends the same email once and shows the same status. When the subscription ends, the 
account closes and the data wipe runs (K39/K51). It must not set a “free” plan (G9; the Free plan was 
retired).
