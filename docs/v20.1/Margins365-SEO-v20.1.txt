3. Rendering: static HTML for public pages (fixes A1)
Google's guidance is that server-side or static rendering is the reliable option, and that dynamic 
rendering (serving bots a different version) is a workaround it no longer recommends (Google: 
JavaScript SEO basics; Google: Dynamic rendering as a workaround).
Requirements
1. Prerender (static generation at build time) or server-render every public route: /, 
/sample-shop, /pricing, /help, /legal/terms, /legal/privacy, /legal/refunds-and-cancellation, 
/legal/dpa, /legal/cookies, the 404 page, and the K76 calculator and K77 landing and help pages 
when they go live. Development chooses the method. 
2. The HTML each route returns before JavaScript runs contains: the full visible text of the 
page (H1, headings, body copy, plan prices, FAQ answers, legal text), the header and footer 
navigation as real links, the page's own <title>, meta description, canonical, robots, Open 
Graph/Twitter tags and JSON-LD (sections 5, 8). The app then hydrates the same markup. 
3. Same content for people and bots. No user-agent switching (cloaking). The prerendered 
page is the signed-out version; signed-in header changes (K67) happen after hydration, in 
space reserved so nothing shifts (CLS, §12). 
4. Live values. The founding "[n] places left" count (K72) is either rendered by the server at 
request time or loaded after hydration in a reserved slot. Prices in the HTML are the standard 
prices plus the founding line exactly as shown to signed-out visitors. 
5. Signed-in app stays client-rendered and is never indexed: /app/*, /account/*, /welcome, 
/invite/* (section 6). 
6. Legal pages are HTML pages (K74). Their Download PDF files are not indexed separately (X-
Robots-Tag: noindex on the PDF responses), so the HTML page is the one that ranks. 
Acceptance: SEO-01, SEO-02, SEO-03.
4. Clean URLs (matches the v20 route map, 23.1)
• One address per page, lower case, hyphens, no trailing slash (except /), no # routing, no 
tracking parameters in internal links. 
• Public routes exactly as 23.1: /, /sample-shop, /pricing, /help, /sign-in, /reset-password, 
/legal/terms, /legal/privacy, /legal/refunds-and-cancellation, /legal/dpa, /legal/cookies. 
• /sample-report (old name) 301 → /sample-shop. 
• Unknown paths return a real 404 status with the branded 404 page (A4), never Home with 
200. 
• Help topics, if they become separate pages later, live under /help/<topic>. 
5. Per-page metadata (fixes A5)
Rules for every public page
• <title> ≤ 60 characters, unique, keyword first and Margins365 (one word) included. Google 
truncates by pixel width, not a fixed count, so ≤ 60 is a safe target (Google: title links). 
• Meta description ≤ 155 characters, unique, a true summary of the page (Google: meta 
descriptions). Google may rewrite it; that is normal. 
• Exactly one H1 per page, matching the page topic; H2/H3 in order without skipping levels. 
• <link rel="canonical"> = the absolute https://margins365.com/... address of the page itself. 
• <meta name="robots"> as in the table. The signed-in app also sends X-Robots-Tag: noindex. 
• <html lang="en-GB">. 
• Founding-offer wording is not put in titles or descriptions (it ends after 100 places and search 
results would go stale).

Serve /robots.txt as text/plain, status 200, with exactly:

Allow: /
Disallow: /app/

Disallow: /invite/

• /sign-in and /reset-password stay crawlable but carry noindex (so the noindex can be seen). 
Reset-token URLs never appear in links or the sitemap. 
• Staging sites send X-Robots-Tag: noindex, nofollow on every response and require a password, 
so they never get indexed. Production must not inherit that header (SEO-07). 
• AI crawlers: no blocking by default (being cited by AI answers helps discovery). Akthar can opt 
out of AI training crawlers later without affecting Google Search.

11. Links, headings, images and accessibility (fixes A3)
• Every navigation item is a real link (<a href="/pricing">), including header, footer, "Start 
here" buttons that go to pages, Sample shop and Help links. Buttons are only for actions 
(submit, open a menu, toggle). Links can still route client-side without reloading. 
• Descriptive link text ("See pricing", "Open the Help centre"), never "click here". 
• Internal linking map: Home → Sample shop, Pricing, Help centre; Pricing → Help centre FAQ, 
Terms, Refunds & cancellation; Sample shop → Pricing; Help centre → Pricing, every legal page; 
every page → footer links (Help centre, Sign in, five legal pages). K76 and K77 pages link to 
Pricing, Sample shop and each other, and Home links to each platform page. 
• Headings: one H1, logical H2/H3 order (also WCAG 2.2 "Info and relationships"). 
• Images: every content image has an alt describing it ("Sample shop Control room showing a 
Health Score of …"); decorative images have empty alt. Charts have a text summary nearby. 
Width and height set to prevent layout shift. 
• Images in WebP or AVIF with a fallback, sized for the screen (srcset), lazy-loaded below the 
fold, the hero/LCP image never lazy-loaded. 
• These overlap with WCAG 2.2 AA (spec 15): lang attribute, link purpose, headings, alt text and 
contrast. Lighthouse accessibility is 100 today; keep it there. 
12. Speed: Core Web Vitals (fixes A8–A10)
Targets (75th percentile, mobile): LCP < 2.5 s, INP < 200 ms, CLS < 0.1 — Google's "good" 
thresholds (Google: Core Web Vitals). Today: LCP 2.9 s (fails), TBT 130 ms (INP can't be measured in a 
lab; TBT is the proxy), CLS 0.079 (passes, small margin).
Requirements
1. Static HTML (§3) so text paints before JavaScript downloads. 
2. Split the JavaScript: public pages must not download the signed-in app, charts or import code. 
Target ≤ 150 KB compressed JS on public pages (today 256 KB, with about 164 KB unused). 
3. Cache hashed files in /assets/ for one year (public, max-age=31536000, immutable) and let 
Cloudflare cache them. Cache prerendered public HTML for a short time (for example 5 
minutes) and purge on deploy. Signed-in and API responses stay private, no-store. 
4. Preload the main font (or use a system font stack), font-display: swap; preconnect only to 
origins actually used on the first view. 
5. Reserve space for the signed-in header, founding counter and any banner (CLS). 
6. Do not call the session check on public pages for signed-out visitors in a way that logs a 
console error (A10); a quiet "not signed in" response is fine. 
7. Security headers on every HTML response: HSTS, X-Content-Type-Options: nosniff, Referrer-
Policy: strict-origin-when-cross-origin, frame protection (frame-ancestors 'none' in CSP or X-
Frame-Options: DENY), and a Content Security Policy that allows Stripe and Google sign-in. 
Already QA SEC-20–24. 
8. Measure with Lighthouse on Home, Pricing, Sample shop and Help centre before each release; 
after launch, watch the Search Console Core Web Vitals report (real users). 
13. Search Console, Bing and analytics consent
Google Search Console (Akthar's Google account owns it; developers get user access):
1. Add a Domain property for margins365.com, verified with a DNS TXT record at the DNS provider 
(Cloudflare). 
2. Submit https://margins365.com/sitemap.xml. 
3. URL-inspect and Request indexing for each public page after launch. 
4. Watch: Page indexing (soft 404s, duplicates), Core Web Vitals, HTTPS, Enhancements 
(Breadcrumbs), Manual actions. 
Bing Webmaster Tools: import the site from Search Console (fastest) or verify with DNS; submit the 
same sitemap. Bing's index also supplies results to Yahoo and several smaller search engines. 
Optional: IndexNow to tell Bing about updates instantly.
XML sitemap at /sitemap.xml (application/xml, 200): only the indexable public pages in §5.1 (/, /sample-
shop, /pricing, /help, the five /legal/... pages, and Part D pages once live), absolute 
https://margins365.com URLs, a real lastmod from the last content change. No priority or changefreq 
(Google ignores them). Never signed-in, sign-in, reset or PDF URLs.
hreflang: the site has one language. Add hreflang="en-GB" and hreflang="x-default", both pointing to 
the page itself, on every public page and in no other form. Google says hreflang is only needed for 
alternative language or region versions, so this is tidy rather than a ranking factor. Add other 
languages only with separate translated pages later.
Analytics and cookies (K79, approved). Search Console and Bing need no cookies and no code on 
the page. Analytics uses Plausible Analytics (EU-hosted, no cookies, no stored IP addresses) and 
loads only after the visitor clicks "Accept analytics" on a consent banner with equal Accept and 
Reject buttons, for UK and EU visitors alike. No analytics in the signed-in app. The Cookie notice, 
Privacy Policy and DPA page move to v20.1 in the same release. Full requirements: spec 23.18.
• Background on the law: in the UK, since the Data (Use and Access) Act 2025, analytics used 
only for aggregate statistics can run without prior consent if visitors are told and can opt out 
(ICO: exceptions); EU ePrivacy rules are stricter. Gating on consent meets both.
